# MocapLive — SlimeVR 实时动捕 → Unitree G1

把「人穿惯性动捕服」的动作，**实时**变成 G1 的 29 个关节目标：
SlimeVR(VMC/UDP) → 坐标归一 → GMR 重定向(IK) → 安全限幅 → MuJoCo 仿真 / DDS 真机。

- 重定向**不自己写**：直接用开源的 [GMR](https://github.com/YanjieZe/GMR)（MIT）。
- 仿真**不自己写**：MuJoCo + DeepMind menagerie 的官方 G1 模型。
- 真机**走官方通道**：`unitree_sdk2py` 的 `rt/lowcmd`，网卡问题沿用你项目里验证过的 IPv4 绑定法。
- 本项目自己写的只有三样：**VMC 适配层**、**实时流水线（缓冲/限幅/看门狗/录制）**、**界面**。

```
        ┌──────────── 60Hz 实时 ────────────┐
SlimeVR ─VMC/OSC─▶ 14 点人体帧 ─▶ GMR(IK, 2~5ms) ─▶ 29 关节 ─▶ 限位/限速 ─┬─▶ MuJoCo 仿真
 (UDP 39539)         Unity→Z-up                                          └─▶ G1 真机 (DDS)
                          │                                                  │
                          └────────── 录制 → 36 列 CSV → 训练 ◀──────────────┘
```

## 二、三种用法

### A. 没硬件，先看效果

```bat
3_假动捕发送端.bat          :: 它按 VMC 协议发"假 SlimeVR"
1_启动界面.bat              :: 界面里源选 SlimeVR(VMC)，点启动
```
等价于命令行：`python -m mocap_live.cli --source synthetic --output sim`

### B. 接 SlimeVR（正式用法）

0. **先跑 `5_连接诊断.bat`**，它会给你结论，而不是一堆原始数据：

   | 结论 | 含义 | 怎么修 |
   |---|---|---|
   | ❌ 一条 VMC 数据都没收到 | 端口/地址错，或 VMC 没开 | Port Out=39539、Address=127.0.0.1、勾 Enable，改完重启 SlimeVR |
   | ⚠ 只收到 5/14 个关键点 | 没加载 VRM，SlimeVR 只发了跟踪点 | 见下表最后一行 |
   | ✅ 14 个关键点齐全 | 通了，直接启动界面 | — |

1. **SlimeVR Server 里必须做**（少一步就只有 5 个点、没有完整骨架）：

   | 位置 | 设成 |
   |---|---|
   | Settings → OSC/VMC → Enable | 开 |
   | Port Out | **39539** |
   | Address | `127.0.0.1`（或本机 LAN IP） |
   | **VRM Model** | **一定要拖一个 VRM 进去** |

   > 官方说明：不加载 VRM 时 SlimeVR 只发跟踪点、锚点也不完整，VMC 输出会缺四肢。
   > 随便一个 VRM 都行，它只是用来做骨骼映射的。

2. 启动界面 → 源 = `SlimeVR (VMC/UDP)`，端口 `39539` → 启动。
3. 戴好、站直、**面朝你想让机器人朝的方向**再连。程序的朝向归一化是拿"第一帧的骨盆 yaw"当基准的。
4. 收不到数据就用 `4_VMC抓包.bat`：一条都不打印 = 端口/地址填错；打印了但名字怪 = 把名字发我，改 `frame.py` 的 `VMC_ALIASES` 即可。

### C. 上真机（先读完第五节）

```bat
1_启动界面.bat
:: 界面里：输出 = G1 真机 (DDS) → 启动 → 看到"源 60Hz"后 → 点「使能真机」
```

或命令行（会 3 秒后自动使能，危险动作请用界面）：

```bash
python -m mocap_live.cli --config configs/g1_real.yaml --activate
```

## 四、5 点动捕（你现在的配置）

只有 **胸 + 双大腿 + 双小腿** 5 个 IMU 也能跑，但 GMR 的 IK 需要 14 个身体，中间那些点由
`mocap_live/complete.py` 用骨架补出来：

| 你测的（真实） | 推算的 | 推算依据 |
|---|---|---|
| 胸、左右大腿、左右小腿 | 骨盆、左右脚、双臂、手腕 | 骨长比例 + 父子层级传导 |

上臂/前臂没有任何 IMU，所以**手臂是固定的自然下垂姿态，不会跟着你动** —— 这不是 bug，
是 5 点的物理上限。想要手臂跟，加 2 个手臂 tracker 后把「点位数」切成「自动」。

### 用法

1. **站直**，再点「启动」（首帧姿态会被当成"站直参考"，这是校准）
2. 如果启动时你正好弯着腰 → 站直后点一次 **「重新校准（站直后点）」**
3. 界面右下角会显示：`5点补全 5/14 真实，推算: Hips,LeftFoot,...`

无硬件想看效果：`python -m mocap_live.app --demo-points 5 --autostart`

### 为什么必须校准

VMC 给的是 Unity 骨骼的世界四元数，每根骨骼的局部轴约定（+Y 沿骨、+X 朝哪）和我们的骨架不一致，
直接套会把四肢拧歪。校准只做一件事：记下静止时每根骨骼的朝向 `q0`，之后用
`q_now · q0⁻¹` 拿"相对静止转了多少"——这个增量与轴约定无关，顺手也解决了"开机朝向随机"。

### 想加点位？先看这张表（同一套动作，只改"可信点"）

| 配置 | 手部位置误差 | 说明 |
|---|---|---|
| 5 点（胸+双大腿+双小腿） | 8.5 cm | 手臂完全推算 |
| + 双**大臂**（你说的 8 点） | 6.4 cm | 整条手臂会跟着摆，但**肘角仍是猜的** |
| + 双**肘/小臂**（SlimeVR 官方 7 点做法） | ≈0（理论） | 前臂位置+朝向都已知，手就是前臂延长 |

结论：**加"肘部（小臂）"比"大臂"值一个数量级**。SlimeVR 官方的 Full-Body Set 用的就是 elbow 而不是 upper arm。
腰部 tracker 的价值不在手，而在 **root 姿态**（转身/扭腰时骨盆朝向从"由胸反推"变成实测）。

改成自定义点位（不用改代码，配置文件里写）：

```yaml
source:
  point_mode: "auto"
  trusted: ["Hips","Chest","LeftUpperLeg","RightUpperLeg","LeftLowerLeg","RightLowerLeg",
            "LeftLowerArm","RightLowerArm"]     # ← 加了肘部 tracker 就这样写
```

### 校准（这一步做错，后面全是歪的）

| 阶段 | 程序行为 |
|---|---|
| 启动后 | 显示黄色横幅"校准中 n/20，请站直别动"，**期间一帧都不下发给机器人** |
| 检测到在动 | 单帧变化 >4° 或整段漂移 >6° → 进度清零重来，提示"检测到在动" |
| 完成 | 20 帧四元数平均（半球对齐）→ 记下每根骨骼的静止朝向 |
| 想重来 | 界面「重新校准（站直后点）」 |

为什么必须站直：校准把"你此刻的姿态"定义为骨架的原点。弯腰/半蹲时校准，机器人就会一直保持那个歪姿态。

### 实测精度（用同一套骨架做真值，只喂 5 点再比对）

| 点 | 类型 | 平均误差 | 最大 |
|---|---|---|---|
| 骨盆 | 推算 | 0.5 cm | 0.7 cm |
| 胸 | 真实 | 0.0 cm | 0.0 cm |
| 左右脚踝 | 推算 | 1.0 cm | 1.6 cm |
| 左右手 | 推算 | 8.5 cm | 15.4 cm（手臂本来就没测，属预期） |

端到端：60Hz、IK 2.7 ms、延迟 9.6 ms（5 点比全量多约 5 ms，因为多了补全那一步）。

## 五、关于"未来帧"（就是你截图评论区那个问题）

那位 UP 主回答"重定向然后给关节 pos"、"有给未来帧的观测"。这件事在实时系统里有个绕不开的矛盾：

> 策略如果要观测 `t+Δ` 的参考轨迹，你就必须**等**到 `t+Δ` 才能算 `t` 的动作 —— 也就是**主动加 Δ 的延迟**。

本项目的做法是把它变成一个显式参数 `app.lookahead_ms`：

| 取值 | 行为 | 延迟 | 适合 |
|---|---|---|---|
| `0`（默认） | 参考帧直通，永远用最新一帧 | 3~5 ms | 纯运动学直通、只看动作 |
| `150~200` | 输出整体后移 Δ，环形缓冲里真的存着"未来"的参考帧 | +150~200 ms | 喂给需要 future window 的跟踪策略（wbc_fsm / rl_sar） |

实测：`lookahead=0` → 延迟 3.6 ms；`lookahead=150` → 152.8 ms（开关确实生效）。

参考帧缓冲在 `Pipeline._ref_buf`（600 帧 @60Hz = 10 秒），策略侧要取 `t+k` 直接从这里捞。

## 六、真机安全（必读，出问题会摔机）

### 官方指令面板（界面「机器人」标签页）

不用再开 Unitree App —— 这些按钮走的就是 App 同一条 RPC 链路：

| 按钮 | 底层调用 | 作用 |
|---|---|---|
| 查状态 | `MotionSwitcher.CheckMode` + `LocoClient.GetFsmId` | 看当前是运控还是调试模式、FSM 号 |
| ① 进调试模式 | `CheckMode` → `ReleaseMode` 循环直到 name 空 | 释放 ai 运控，`rt/lowcmd` 才开始生效 |
| ② 底层使能 | `rt/lowcmd`（mode=1） | 我们自己的低层通道接管 |
| 阻尼 / 零力矩 | `SetFsmId(1)` / `SetFsmId(0)` | 变软 / 完全松 |
| 蹲→站 / 躺→站 / 坐下 | `SetFsmId(706)` / `702` / `3` | 官方起身动作 |

实测（机器人吊挂状态下，2026-11-24）：

```
① ai 运控 → ② 释放运控：code=0，模式变"无（调试模式）"，lowcmd 可用=是
③ 低层使能：使能电机 0/29 → 29/29（电机要收到第一帧 lowcmd 才切 mode=1）
④ 台阶验证：左肘 +5° 指令 → 实际 +3.5°（kp_scale=0.8，重力下垂属正常），回位准确
⑤ 阻尼退出 → ⑥ 交还运控：SelectMode("ai") code=0，模式回到 ai
```

> 两个时序坑：
> - **使能电机数**：必须在开始发 lowcmd 之后再统计，否则永远是 0/29。
> - **交还运控**：刚停 lowcmd 时第一次 `SelectMode` 常返回 `7002`，重试 1~2 次即成功，代码里已做 5 次重试。
>
> 机器人站立（IMU rpy≈0、陀螺仪≈0）时点「释放运控」会立刻失去支撑 —— 先吊挂。

### ⚠ 曾经漏掉的一步：CRC

`unitree_hg` 的 `LowCmd_` 有 `crc` 字段，官方例程每帧都算：
`cmd.crc = CRC().Crc(cmd)`。不算是**不会报错**的——机器人直接静默丢弃。
本项目已补上（阻尼帧和正常帧都算）。

### 联调三步（顺序别乱）

1. **`python tools\g1_check.py`** —— 只订阅不发布，确认网卡/mode_machine/电压/温度/使能电机数。
   输出里 `使能电机 0/29` 说明机器人在普通模式，**必须先切到调试模式（lowlevel）**，否则 `rt/lowcmd` 会被忽略。
2. **启动界面 → 选真机 → 启动**：这时只建立 DDS、显示状态，**不发任何指令**。
3. **站直 → 点「使能真机」**：会用"此刻的机器人姿态"和"此刻的动捕站姿"做**零位对齐**
   （两者之差 ≤20° 才允许，超过直接拒绝并告诉你差多少度 —— 机器人还躺着时别硬来）。

### 零位对齐是什么

机器人关节零位、装配误差、人体比例和模型不可能完全一致，直接下发会整体歪几度。
使能瞬间算 `offset = 机器人当前关节角 − 动捕站姿关节角`，之后所有指令都加这个 offset，
所以**第一帧下发 = 机器人当前姿态**，不会跳。`offset > 20°` 会限幅并告警；`> 34°` 直接拒绝使能。


1. **机器人必须在调试模式（lowlevel）**。普通运控模式下 `rt/lowcmd` 不生效——这是保护，不是 bug。
2. **必须吊挂**。这套是纯运动学重定向，没有任何平衡控制；地面不平时它就是会摔。
3. **第一次先 `kp_scale: 0.7`**，看关节跟踪稳了再回到 1.0。
4. 程序里已经加的四道闸（`core/safety.py`）：
   - 位置夹在硬限位内，再留 3°（真机配置 4°）
   - 速度限幅：取 `min(关节速度上限, 20 rad/s)` —— **髋 roll 实机只有 20，旧 URDF 写的 32 是错的**
   - 单帧跳变限制 8°（真机）/ 12°（仿真）：IK 偶尔会蹦一下，不拦会打断减速器
   - 看门狗 250 ms：断流就**冻结在最后姿态**，不外推、不猜
5. 急停后需要重新「使能」才会继续发指令。

## 七、录制 → 训练（接你现有的链路）

点「录制」得到的文件在 `records/`：

| 文件 | 内容 | 用途 |
|---|---|---|
| `<时间>_36col.csv` | 60Hz，`root_xyz(3) + quat_xyzw(4) + 29 关节`，无表头 | 和你 `pipeline/rlsar_export.py` 的输出**完全同格式**，可直接喂 rl_sar / mimic 训练 |
| `<时间>_human.pkl` | 原始人体帧（14 点） | 用 `--source replay` 复现同一段动作，对比不同 IK 参数 |

**回放任何 BVH**（不用管是 LAFAN1 还是 SlimeVR 命名）：

```bash
python -m mocap_live.app --replay "D:/DATAWORK/G1/bvh-recording.bvh"
```

- 名字大小写/下划线不敏感（`LEFT_FOOT` / `LeftFoot` / `left_foot` 都认）
- 厘米/米自动判断；Y-up 自动转 Z-up
- 点数不足 14 时自动补全，**校准参考用 BVH 自带的 rest pose**（比拿首帧准）
- 1800 帧加载约 0.6 s（FK 全帧向量化，之前逐帧 Python 要 12 s）

回放：

```bash
python -m mocap_live.cli --source replay --replay records/xxx_human.pkl --output sim
```

## 八、参数怎么调

| 参数 | 默认 | 说明 |
|---|---|---|
| `source.point_mode` | `5` | `5`=只信胸+双大腿+双小腿，其余推算；`auto`=收到什么信什么（有手臂 tracker 时用这个） |
| `source.completion` | true | 关掉就必须自己给满 14 点 |
| `retarget.human_height` | 1.75 | 填**真实身高**，重定向的肢体缩放靠它 |
| `retarget.smooth_alpha` | 0.55 | 位置 EMA。抖 → 调小（0.4）；慢半拍 → 调大（0.7） |
| `retarget.lock_xy` | true | 开：人走机器人原地；关：机器人跟着人在世界里平移（真机别关） |
| `retarget.offset_to_ground` | false | 开：每帧把人贴地（会吃掉跳跃） |
| `safety.max_jump_deg` | 8~12 | 关节单帧最大跳变，越小越安全越"粘" |
| `output.kp_scale` | 1.0 | 真机跟踪不稳先降到 0.7 |
| `app.control_hz` | 60 | 重定向+下发频率（DDS 内部再按 500Hz 重发） |
| `app.lookahead_ms` | 0 | 见第四节 |

## 九、排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动弹 `UnicodeDecodeError: 'gbk' codec can't decode byte 0xa8` | GMR 读 IK 表用 `open()` 不带编码，中文 Windows 按 GBK 解 | **已修**：IK 表改为纯 ASCII + `PYTHONUTF8=1` + 引擎层自动兜底。若还遇到，说明有别的文件被手改成了中文，跑 `python tools/make_ik_config.py` 重生成 |
| 回放报 `KeyError: 'LeftFoot'` | GMR 自带 BVH 解析器只认 LAFAN1 命名 | **已修**：改用 `mocap_live/bvh.py`，任意 BVH 命名都认 |
| 机器人倒立 / 左手跟右手 | Unity(左手系) → Z-up 用纯旋转会镜像 | **已修**：改用反射矩阵 `frame._UNITY_M`；自检里有"上轴/左右"两项检查 |
| 界面一直"源 等待数据…" | SlimeVR 没开 VMC / 端口反了 / 地址不对 | 跑 `5_连接诊断.bat`，它会直接给结论 |
| 收到数据但姿态塌成一团 | SlimeVR 没加载 VRM，只发了 5 个点 | 按第二节 A 的表格加载 VRM |
| 机器人整体转向了 | 连上时人没朝正前方 | 断开重连（首帧朝向就是基准） |
| 机器人跟着人走，撞墙 | `lock_xy` 关了 | 打开 |
| 手臂僵着不动 | 5 点配置里没有手臂 IMU | 正常现象；加手臂 tracker 后点位数改「自动」 |
| 机器人整体比人矮一截 / 腿伸不直 | 校准时没站直 | 站直后点「重新校准」 |
| 关节一直贴限位（红色） | 身高填错 / 动作超出 G1 能力 | 改 `human_height`；深蹲类动作本来就会顶到限位 |
| `连不上 rt/lowstate` | 网卡没选对 / 不是 192.168.123.x | 看 `outputs/dds_g1.py` 的自动选网卡，或手填网卡名 |
| 控制频率上不去 | 机器太慢 | 降 `control_hz` 到 50；关掉 3D 预览 |

## 十、IK 表为什么自己生成了一张

`configs/ik/slimevr_pos_to_g1.json` 是从 GMR 自带的 `xsens_mvn_to_g1.json` 改出来的：

| 项 | GMR 原表（Xsens） | SlimeVR 表 |
|---|---|---|
| 骨盆 | 位置 10 / 朝向 10 | 朝向 **100**（整机朝向必须锁死） |
| 躯干 | 朝向 100 | 朝向 **20**（够用即可，防止上身乱扭） |
| 四肢 | 朝向 100/10（按 Xsens 骨骼局部轴调过） | **朝向 0，纯位置 IK** |

原因：Xsens 和 Unity 人形骨骼的局部轴约定不同，直接套原表会把胳膊拧成"小臂前伸"。
动捕给的**位置**是约定无关的，所以四肢只跟位置，姿态由 IK 自己解。
实测（合成走路）：脚部前后相关 1.00，左右不串；髋高 0.75 m；IK 1.8~3.9 ms。

要重新生成或微调：

```bash
python tools/make_ik_config.py       # 改 tools/make_ik_config.py 里的权重常量
```

> 注：G1 的肘关节零位本身是"弯 90°"的（模型零位前臂朝前），所以界面里显示"左肘 +64°"
> 不代表机器人折了个 64° 的角，别被数字吓到 —— 看 3D 预览最直观。
